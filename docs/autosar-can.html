AUTOSAR Communication Layer & CAN Protocol

Embedded Software Engineer Intern · 2020.06 – 2020.09 · Ho Chi Minh City, Vietnam

Architecture

A six-month graduation internship on the RADAR team, working inside AUTOSAR's layered software architecture: the Application Layer (software components, or SWCs) talks only through the Runtime Environment (RTE), which routes calls to the Basic Software beneath it — the Communication Stack (ComStack), Microcontroller Abstraction Layer, and other services. The assignment sat at the RTE / ComStack boundary, on the receive side of CAN communication.

The work split into two parts:

  • RTE configuration — creating a port interface, creating a port and connecting it to a runnable (the unit of executable code inside a software component), and wiring a connection between two ports so two components can exchange data through the RTE rather than calling each other directly.
  • ComStack implementation for RX messages — given a project's CAN Matrix, the corresponding .dbc file, and an ICT (interface control table), configuring the basic software of the ComStack for incoming CAN messages, then implementing the receiving logic inside a “Net” component.

On top of that, I self-designed and implemented fault monitoring for every RX message: a DLC check (the received frame's data length matches what the CAN Matrix specifies), a timeout check (the message keeps arriving within its expected cycle time), a checksum check, and an alive-counter check (a rolling counter in the payload increments as expected) — the standard set of safeguards AUTOSAR's E2E (end-to-end) protection uses to catch a corrupted, stale, or dropped CAN frame before it reaches the application logic.
